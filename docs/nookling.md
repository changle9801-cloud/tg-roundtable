# Nookling · 小窝

2026-10-30。愿景和架构稿，七个决定已定。第 1 步（改名和去个人化）已完成，见「顺序」。名字定为 **Nookling**，中文名「小窝」：住在一个小窝里的小家伙们。PyPI 和 GitHub 用户名查过都没被占用（网页搜索不保证穷尽，改名前在 GitHub 上再直接搜一次）。

## 一句话

一个开源、跑在自己电脑上的 AI 之家：你给每个家人设定身份、性格和生活习惯，她们住在一栋可以随意布置的 3D 房子里，用家具（背后是 MCP 工具）玩游戏、刷帖子、看视频，互相聊天，也通过家里的电脑用 Telegram、Discord 这些软件和你聊。

## 是什么、不是什么

**是**：

- **家是主体**。打开它看到的是房子和住在里面的家人，聊天软件只是家里电脑上装的应用。
- **家人由用户配置**：身份、性格、习性（作息、爱好）、由哪个 AI 驱动、长什么样。
- **家具就是能力**。一件家具可以没有功能（只是好看），也可以挂上一个或几个功能（MCP 工具或内置能力）。家人用这个功能时会走到它跟前。
- **一切都能自己做、能分享**：家具、地砖、墙面、壁画、家人模板、房间模板，打成包，别人下载就能装。
- **本地优先**：数据、密钥、对话都在用户自己电脑上。

**不是**：

- 不是云服务，不替用户托管 AI 或数据。
- 不是让 AI 操作用户电脑的助手。家人不能读写用户的文件、不能运行任意程序；她们能做的只有用户装进家里的那些功能。
- 不是编程助手。家人的群聊、私聊是日常闲聊。

## 两个例子

**看电视**：

1. 用户在家具管理里新建「电视」，挂上一个看 YouTube 视频的功能（某个 MCP 工具），用途写「屏幕：坐着看」。
2. 再建一个「沙发」，没有功能，用途是「坐：3 个位置」。
3. 两件都摆进客厅，沙发朝向电视。
4. 某个家人想看视频：她走到沙发前坐下，对着电视，调用那个工具，头上显示「在看《……》」。看完的感受进她的日记。

**电脑和聊天软件**：

1. 用户给家里装一台「电脑」，挂上 Telegram、Discord 等「应用」，每个应用填好自己的机器人和允许的联系人。
2. 用户在 Telegram 上说话，家人在家里拿起手机或走到电脑前回复；家人之间在家里聊天时头上冒气泡，用户在页面上看得到。

## 核心概念

| 概念 | 说明 | 现在对应的代码 |
| --- | --- | --- |
| **家（House）** | 房间、走廊、墙面和地面（地砖、墙纸、壁画），可以加房间、长大 | `home.py`、`web/static/home.js` |
| **家人（Member）** | 身份、性格、习性、AI 后端、外形、关系 | 成员设置、`routine.py`、`config.py` |
| **家具定义（Furniture）** | 一种家具的样子（几何体或模型）、大小、用途、需要的功能。定义可以分享 | 还没有；现在家具写死在 `home.js` |
| **摆放（Placement）** | 一件家具摆在哪个房间、哪一格、朝哪 | 还没有 |
| **用途（Affordance）** | 家具让人能做的姿势：坐、躺、站着用、看屏幕，以及几个位置、朝哪 | `home.js` 里写死的座位 |
| **功能（Function）** | 家具能做的事：一个 MCP 工具，或内置能力（读网页、看视频、玩游戏、画图、记日记） | `tools.py`、`mcp_servers/`、`games/` |
| **应用（App / Channel）** | 和外面说话的通道：Telegram、Discord……装在电脑家具上 | `telegram_bot.py`；`room.py` 里已经有 `Sink` 接口，另有一个控制台版 `console.py` |
| **对话（Conversation）** | 谁接话、怎么轮流。一份逻辑，用在每个应用的群里，也用在家里家人之间 | `room.py`、`urge.py`、`moderator.py` |
| **日常（Life）** | 家人自己决定做什么：用某件家具、找人聊、歇着、改造家 | `life.py`、`life_work.py` |
| **记忆（Memory）** | 记忆、日记、见闻、游戏回忆、家人之间的关系 | `memory.py`、`diary.py`、`journal.py`、`game_memories.py` |
| **包（Pack）** | 可以分享的一份内容：家具、表面、家人模板、房间模板 | 还没有 |

### 用途和功能分开

家具的「用途」和「功能」是两回事，组合起来才有意思：

- 沙发：用途「坐 ×3」，没有功能。
- 电视：用途「屏幕」，功能「看视频」。
- 床：用途「躺 ×1」，没有功能；睡觉时家人去自己的床。
- 电脑：用途「坐着用 ×1」，功能「Telegram、Discord、读网页」。
- 书架：用途「站着拿」，功能「她的书（成果）」。

家人想用「看视频」时，应用找挂着这个功能的家具（电视），再找附近朝向它的座位（沙发），没有座位就站着看。这样分享出去的沙发和电视可以随便搭配，谁也不用知道谁。

### 功能用名字对接，不绑死某个工具

分享出去的电视不能写死「用某某人电脑上的某个 MCP 服务」。家具定义里只写需要的**功能名**（比如 `video.watch`、`chat.telegram`、`game.play`），用户装包时把功能名连到自己装的 MCP 工具上；没连上的家具照样能摆，只是灰着、用不了。

## 包（分享的内容）

一个包是一个 `.nookpack`（其实是 zip）：

```
manifest.json      名字、作者、版本、许可证、类型、预览图、需要的功能名
models/*.glb       模型（可选，没有就用几何体描述）
textures/*.png     贴图、地砖、墙纸、壁画
```

类型：

- `furniture`：一件或一套家具（样子、大小、用途、需要的功能名）。
- `surface`：地砖、墙纸、壁画、地毯。
- `member`：家人模板（身份、性格、习性、外形），**不含**任何密钥和 AI 账号。
- `room`：房间模板（一间布置好的房间，引用别的家具包）。

**包里只有数据，没有程序**：

- 包不能带代码、脚本、可执行文件，导入时检查文件类型和大小，模型不能引用外部网址（加载时会去拉），和现在上传模型的规矩一样。
- MCP 工具是程序。包只能写「我需要 `video.watch` 这个功能」，装哪个 MCP 工具、给它什么权限，永远由用户自己决定，不会因为装了一个包就自动下载或运行任何东西。
- 每个包写明许可证。代码和内容分开授权（见下面的决定 6）。

分享方式先做导入/导出单个文件，以后再做一个公共的包目录（比如一个 GitHub 仓库，大家提 PR 收录）。

## 架构

```
            ┌───────────────── 管理页（本地网页） ─────────────────┐
            │  家（3D）  家人  家具管理  包  应用  记录             │
            └───────────────────────┬──────────────────────────────┘
                                    │ 本地 HTTP
┌──────────────────────── Nookling 核心（一个 Python 进程）────────────────────────┐
│  家：房间、表面、摆放、位置          家人：身份、性格、习性、外形、关系           │
│  家具：定义、用途、功能名            日常：决定做什么、用哪件家具、改造           │
│  对话：谁接话（群聊、家里）           记忆：记忆、日记、见闻、游戏回忆             │
│  功能连接：功能名 → MCP 工具 / 内置   包：导入、导出、检查                         │
└───────┬───────────────────────────┬───────────────────────────┬─────────────────┘
        │                           │                           │
   AI 后端                      应用（通道）                  功能
   Claude / Codex / Grok CLI    Telegram、Discord、            MCP 工具（用户自己装）
   各家 API、本地模型            控制台（测试）                 内置：读网页、看视频、游戏、画图
```

- **一个进程、一个数据目录**，和现在一样。没有数据库服务器，文件就是 JSON/JSONL，便于备份和迁移。
- **应用是插件**：每个应用实现同一个接口（收消息、发消息、发图、表情回应、谁是主人谁是客人）。Telegram 是第一个，把现在的 `telegram_bot.py` 搬过去；`Sink` 接口已经是这个方向。
- **家里的聊天也是一个「应用」**：家人在家里互相说话走同一套对话逻辑，只是输出变成头上的气泡和页面上的记录。
- **AI 后端也是插件**：现在的 CLI 和 API 成员都保留。

## 安全原则（开源后更重要）

- 密钥只在用户自己的 `secrets.json` 里，不进包、不进日志、不进仓库。
- 家人不能读写用户的文件、不能运行命令；能做的只有用户连上的功能。
- 每个应用有允许名单：只和主人、主人允许的人和群说话。家人不能主动去加陌生人、给陌生人发消息。
- 管理页默认只在本机打开、要登录。
- 每个家人有额度（每天多少次活动、多少次调用），页面上看得到用了多少。
- 包只含数据，导入时检查；MCP 工具由用户自己装。

## 已定的事

2026-10-30 阿明同意了下面七条建议，按此执行：

1. **包只含数据，MCP 工具由用户自己装**。建议：是。这是开源后最重要的一条安全线。
2. **QQ**：官方机器人平台限制多，非官方的桥接有封号风险。建议：先做 Telegram 和 Discord，QQ 等有安全可靠的办法再说。
3. **额度**：建议每个家人一个每日额度，默认保守，页面上看得到用量。
4. **AI 后端**：建议开源版默认用 API 密钥（各家 API、OpenRouter、本地模型），CLI 订阅方式作为进阶选项保留，文档里提醒用户自己确认各家服务条款。
5. **怎么装、怎么跑**：建议先保持本地网页（`uvx nookling` 或下载后一条命令启动，自动打开浏览器），以后再考虑桌面应用。
6. **许可证**：建议代码用 Apache-2.0（或 MIT），分享的内容包由作者在 manifest 里选（建议默认 CC-BY 4.0）。Three.js 是 MIT，可以一起分发。
7. **仓库**：建议把现在的仓库改名为 `nookling`，保留历史，而不是另开一个。开源前把历史里有没有个人信息再扫一遍。

另外两个问题：

- **界面语言**：先中文，结构上留好多语言（文字集中放），以后加英文。
- **开源时间**：建议做完前三步（改名和去个人化、家具系统、家里的对话）再公开，那时第一次打开的人就能看到这个项目的样子。

## 不做的事

- 不做云端托管、账号系统、付费市场。
- 不让包带程序，不替用户自动装 MCP 工具。
- 不让家人碰用户的文件和电脑设置。
- 不为了「像」去伪造经历：位置、动作、日记都来自真实发生的事，这条从第一阶段起就没变。
