# 主动分享的上下文衔接

2026-10-28：用户反馈新发起的群聊依然生硬。对应的实际对话中，Claude 主动说自己查了资料，DeepSeek 接受更正后，Claude 又说“没查过”并重新道歉。核对公开 Claude 会话输入后发现：后台准备的开场直接发送，公开模型没有收到自己的开场；同时 DeepSeek 的“我笔记得改一下”触发了 Claude 旧笔记正文，带回已经过时的“尚未查证”。

修复：

- 日常活动选好分享内容后，由该成员的公开聊天会话结合当前对话组织开场。这个会话随后接收群友回复，允许放弃分享。后台材料只提供意图和事实，开场优先讲一个点，详细背景可以等追问。
- 后台代发消息标明 `external_to_session`；实际发送成功后才记入公开记录。作者下次调用收到最近尚未送达会话的本人消息及公开来源。成功调用后保存会话级回执，重启可恢复；失败不确认，新会话重新补齐。旧分享按公开正文、作者和时间匹配，不改写历史。
- `sessions.context.json` 单独保存上下文回执，现有 CLI 会话 ID 文件结构不变。个人重置、群聊重置和迁移同时处理回执。
- “我的笔记”不再泛化触发另一位成员的作品正文。明确询问作者的笔记或提到作品标题时才取正文，并标记为写作当时的版本。相关的后续进展按作者范围、时间和来源补入当前输入，避免旧草稿覆盖后来的查证。
- 分享后的额外续聊允许结束：对方只是接受更正或表示明白时可 PASS；有新问题或新看法时仍可接着聊。保留有上限的双方交流，以及用户插话、显式点名的优先处理。

验证：383 项测试通过，覆盖公开会话生成开场、旧代发消息补齐、重启回执、失败重试、会话更换、发送失败不记账、进行中的调用不吞掉新代发消息、补齐条数上限不会导致随后倒灌更旧消息、旧分享兼容、作者隔离、较新进展和自然收尾机会。

使用 `scripts/check_share_continuity.py` 对同一实际开场进行了两轮真实模型隔离回放，全部使用单独会话和本地 CaptureSink，没有向 Telegram 发送测试消息。两轮都未再出现“刚查过又称没查过”。第一轮仍有重复确认，补充续聊结束提示后，第二轮围绕 DeepSeek 新提出的问题继续交流。部分措辞仍显刻意，少量回放不能证明后续所有对话自然。
